# laya-trader-binance

Leakage-aware dataset and fine-tuning pipeline for specializing [Laya](https://github.com/NandhaKishorM/laya) as a fast typed decision model for crypto trading.

This repository deliberately **does not contain live Binance order execution yet**. The first milestone is to prove that a fine-tuned Laya checkpoint has out-of-sample trading edge after explicit costs. Only then should a live executor be added.

## Decision contract

At candle close `t`, the model sees only information available through that close. The simulated entry used for the label is `open(t+1)`. The future is used only by the label generator.

Laya is trained on three typed questions in one state:

- `action`: `LONG | SHORT | FLAT`
- `tradeable`: `false | true`
- `edge_quality`: ordinal score `0..4`

Targets are soft probability distributions derived from deterministic trade outcomes. They are not generated by an LLM.

## Dataset v1

Default source: Binance public **USD-M Futures** monthly klines at `15m`.

State features are causal and normalized/discretized before being serialized for Laya. The default context includes the base timeframe plus `1h` and `4h` views.

The label policy is a triple-barrier variant:

- decision: close of candle `t`
- entry: open of candle `t+1`
- default horizon: 16 x 15m = 4h
- take profit: `+2 ATR`
- stop: `-1 ATR`
- configurable round-trip fee/slippage assumptions
- `FLAT` has zero utility; directional actions must beat `min_edge_r`
- if TP and stop are first touched in the same candle, the sample is ambiguous and is dropped by default

The temporal splits are fixed and purged:

- train: through 2024-12-31
- calibration: 2025 H1
- validation: 2025 H2
- final test: 2026 through 2026-08-31

A post-boundary embargo is applied, and a sample is only allowed in a split when its complete future label horizon also remains inside that split.

## Setup

Python 3.11+ and `uv` are recommended.

```bash
uv sync --extra dev
```

The project pins the Laya source dependency to the upstream commit used when this pipeline was prepared, so changes in Laya's internal training API do not silently alter the experiment.

## 1. Download Binance data

Edit `configs/dataset.toml`, then:

```bash
uv run laya-download --config configs/dataset.toml
```

Archives are downloaded from Binance's public data archive. If a `.CHECKSUM` file is available, SHA-256 is verified before the archive is accepted.

The long-running download, dataset build, training, calibration, and evaluation commands print timestamped progress to standard output. Each stage shows completed work, elapsed time, and an ETA once throughput can be measured. The ETA is an estimate and can change after GPU warmup or a slow checkpoint save. Training also logs the checkpoint path, size, and save duration; resumed runs start their progress counter at the saved update.

Data is intentionally git-ignored.

## 2. Build the training dataset

```bash
uv run laya-build-dataset --config configs/dataset.toml
```

Outputs:

```text
data/dataset/
├── train.jsonl
├── calibration.jsonl
├── validation.jsonl
├── test.jsonl
├── train.parquet
├── calibration.parquet
├── validation.parquet
├── test.parquet
└── manifest.json
```

The JSONL is the model-facing dataset. Parquet retains numeric diagnostics such as realized R and costs for research/evaluation; those columns are never serialized into the Laya state.

Example JSONL record:

```json
{
  "id": "BTCUSDT:2024-07-15T12:14:59.999000+00:00",
```

## 3. Run leakage tests

```bash
uv run pytest -q
```

The test suite includes a causal-feature test that alters future prices and verifies that an earlier feature row is unchanged.

## 4. Fine-tune Laya

Single GPU:

```bash
uv run laya-train \
  --train data/dataset/train.jsonl \
  --output checkpoints/laya-trader-v0.1
```

Two GPUs / Kaggle 2xT4:

```bash
uv run torchrun --standalone --nproc_per_node=2 \
  -m laya_trader.laya.train \
  --train data/dataset/train.jsonl \
  --output checkpoints/laya-trader-v0.1
```

The first training implementation uses full-model **soft-label supervised fine-tuning plus a proper-scoring regularizer**. This is intentional: our targets are computed directly from market outcomes, so a low-variance supervised objective is a cleaner first experiment than adding policy-gradient variance. We can benchmark RLCD later against the exact same frozen dataset.

Default optimizer groups:

- encoder LR: `2.5e-5`
- decision heads LR: `1e-4`
- epochs: `4`
- max length: `512`
- head budget: `192`

The output checkpoint is laid out so it can be loaded directly by `laya.load()`.

## 5. Calibrate probabilities

Never interpret raw Laya confidence as a trading probability before calibration.

```bash
uv run laya-calibrate \
  --checkpoint checkpoints/laya-trader-v0.1 \
  --calibration data/dataset/calibration.jsonl
```

This fits bounded temperature values on the dedicated calibration split and writes them into `rl_agent_config.json`. It also writes `calibration_report.json` with NLL before/after calibration.

## 6. Inference

```bash
uv run laya-infer \
  --checkpoint checkpoints/laya-trader-v0.1 \
  --state-file example-state.json
```

The runtime uses the same fixed typed questions as training.

## 7. Validate and freeze thresholds

```bash
uv run laya-evaluate \
  --checkpoint checkpoints/laya-trader-v0.1 \
  --data data/dataset/validation.jsonl \
  --selection-data data/dataset/calibration.jsonl \
  --reference-train data/dataset/train.jsonl \
  --output-json outputs/validation_report.json \
  --output-md outputs/validation_report.md \
  --select-thresholds \
  --threshold-output outputs/validation_thresholds.json \
  --batch-size 8
```

Thresholds are selected on calibration data, then applied without retuning to validation data. Both splits require at least `max(100, 0.5% of samples)` nonoverlapping trades per symbol, positive mean R after configured costs, and profitable trades in at least two thirds of the months. A trade conservatively occupies its symbol until the full label horizon ends. If either split fails, no active threshold file is left; an older file is archived with a `stale` suffix. The report also shows overlapping signal metrics for comparison. These metrics are not portfolio PnL and do not include funding or capital allocation.

The saved threshold file is a research candidate, not authorization for live trading. Only after a candidate passes additional execution and cost checks should its frozen thresholds be evaluated on `test.jsonl`. Do not select thresholds on the final test split.

## Rules for experiment integrity

1. Never randomly shuffle train/test before splitting time.
2. Never use a feature whose value requires candles after the decision timestamp.
3. Never allow the label horizon to cross a split boundary.
4. Calibration, validation and final test serve different purposes; do not tune on the final test.
5. Compare trading metrics after costs, not only classification accuracy.
6. Do not enable live order execution merely because in-sample loss improved.
